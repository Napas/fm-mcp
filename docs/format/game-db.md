The date serializer (`0x43fe348`) writes two raw u16s, so the bit layout in "Dates" comes from the struct itself.

Table serializers (`0x32c9e98`, `0x32c9f98`, … `0x32ccd84`) share one template. Each table has its own per-record serializer:

```
table = u32 record_count
        u8  flag                 (table +0x64)
        record × record_count    (type-specific, e.g. 0x3193e28 for the first table)
        trailer                  (0x33e9ea0, shared; not decoded)
```

`memory_pools` counts do not appear one-to-one as table counts. Only the name and person tables are mapped so far (below). Body offsets below exclude the 8-byte inner header.

### Person name tables — verified 26.2.0 (code + bytes)

Just before the person table the writer calls `sub_36d7f10` three times. Each call writes one name table: u32 count, then count × (u32 id, string), with ids 0, 1, 2…

| Table | Count offset | Entries | Example |
|-------|--------------|---------|---------|
| first names | 59 017 120 | 292 706 | "James"; the newest entry is the human manager's "Napas" |
| surnames | 63 553 535 | 597 392 | "Maddison", "Mačiulaitis" |
| common names | 73 168 830 | 93 751 | "Quinn" |

292 706 + 597 392 + 93 751 = 983 849, which is the `PERSON_NAME` pool count. Names are not deduplicated.

The sections before these tables are not decoded, so the parser finds the tables by scanning for a count of at least 100 000, followed by entries 0, 1, 2… holding short UTF-8 strings (`findNameTables`).

### Person table — verified 26.2.0 (code + bytes)

Starts right after the common-name table (body offset 74 963 066). Written by `sub_32cab98(this[0xd])`:

```
u32 count            88 356
u8  flag             0
record × count       one virtual call per object (vtable +0xa8)
trailer              sub_33e9ea0, starts at body offset 121 395 432
```

Each record starts with a class tag byte and ends with a 20-byte trailer:

```
u64 flags | u32 index (0..count-1, in order) | u32 uid | u32 extra (uid again when unset)
```

Person gender: bit 12 (`0x1000`) of the trailer's u64 flags is set for women (verified on every club player of the test save against the club's women's flag).

Bit 3 (`0x8`) of the same word lets the personality rule give negative labels (see "Personality"). Its meaning is unknown. It is set on 96 329 of 139 889 players in the real KŽ save (26.3.2, 2035-12-02), 96 230 of them with uid ≥ 2·10⁹ (hypothesis: hidden attributes generated by the game). The 26.2.0 test save supports this: bit 3 is set on exactly 1 233 players, and they are exactly the players with uid ≥ 2·10⁹, no contract and value −1, i.e. the free agents the game generated (verified, bytes; 3 218 players have uid ≥ 2·10⁹ and no contract). `savefile` exposes the bit as `Player.FlagBit3`; `fm` uses it as the flag of the personality and media handling rules.

Bits 15 (`0x8000`) and 18 (`0x40000`) make the game's transfer-interest check refuse every club: bit 18 in `0x1283a90` (−100 000, reason 6 "retiring" or 60 "considering his options"), bit 15 in `0x1285498` and the free-agent path (−100 000, reason 7 "not interested in any club other than …"); code from the player-interest research. `savefile` exposes them as `Player.Retiring` and `Player.OnlyOneClub`. Bytes (2036-01-16): bit 18 on 35 of 138 955 players, bit 15 on 9; both clear on the 95 players whose interest was checked in game.

Record bodies are not fully decoded, so the parser splits on trailers. It looks for the record's index word preceded by three zero bytes, with a non-zero uid. Attribute bytes can mimic a trailer: records 2 and 6 contain false matches whose "uid" is `0x14140100`. So a match whose uid and extra words are equal wins, and an unequal match is used only when no equal one comes before the next record's trailer. Only record 56 671 needs that fallback. Splitting reproduces all 88 356 indices and ends exactly at the table trailer.
